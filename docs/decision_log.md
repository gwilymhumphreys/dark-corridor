# Dark Corridor — Decision Log

> **For the next agent (or future-me).** Read [`handoff.md`](handoff.md) first — the fresh-agent orientation and the one home of **current build status**. This file records *what was decided, why, and what's open* — so you don't re-litigate settled calls or contradict the model. The dated build chronology lives in [`history/build_log.md`](history/build_log.md).

## How to write an entry

Each entry is one short paragraph: what was decided, why, what it supersedes or
reverses, and a link to the system doc that holds the detail. Keep it under about ten
lines.

The detail goes in the linked doc, not here. That means implementation specifics, file
and directory lists, field names beyond the one or two that carry the decision,
rejected alternatives worked through at length, and refinements made later. Build
status and test counts go in [`history/build_log.md`](history/build_log.md).

Name a rejected alternative in a clause so nobody proposes it again, but do not
re-argue it. The reason for the decision stays here, because that is what stops the
decision being re-litigated; everything else has a better home.

## The approach (keep doing this)

- **One file per system.** `docs/systems/<system>.md`. Cross-system edges live **once** in `architecture.md` → *Interface contracts (boundary hub)*; PRDs link there, never duplicate edges.
- **Incremental.** Foundation + combat-adjacent are PRD'd. **Run-structure (`Run manager` / `Encounter` / `Draft`) is now prototype-scope** — the prototype target is a **playable itch.io build** (see [What’s next](#whats-next)), so it needs the run controller, encounters/events, fights, and localization. **Meta / characters stay deferred** until that build exists (per architecture's "don't write all PRDs up front"). The separate files are *so* we can add layers one at a time.
- **PRD template:** Purpose (is / is-not) → Boundaries (link to hub) → Model & rules → Prototype scope → Open/deferred → Dependencies. Numbers point to source files, never baked into prose. Open questions are **flagged, not invented**.
- **Think-first, then review.** Before writing a PRD, reason through ambiguities, surface *genuine* forks to the user (not conventional defaults), resolve, then write. After writing, consistency-review against the other docs.
- **House style:** sister projects `../battledraft`, `../dogmage` (shared systems, the `Manager` naming). `../a-machine` (= AMTKAG, the dev's shipping game) is the model for the autotest + `tune` patterns.

## Key decisions + why

*(Naming evolved — don't resurrect old terms: `Core`/`Main` → `Timekeeper`; `…controller` → `…manager`; `StatusEngine` → `StatusManager`; `effect`/`pending effect` → `Delivery` + `payload`.)*

1. **`Timekeeper` (was Core/Main).** The combat time system is **combat-scoped** (resets each fight, no meaning outside) — "Core" wrongly implied global/persistent.
2. **`Manager` naming** (house style). Instanced → `class_name FooManager`; autoload → `class_name FooManagerAutoload` registered `Foo`. (`StatusEngine`→`StatusManager`; the two "controllers" → `Run manager` / `Combat manager`.)
3. **Testbed renamed** `main` → `corridor_testbed` (it's a renderer testbed, not the game; frees `main`).
4. **`Combat manager` introduced** — the per-fight orchestrator that nothing owned: the live fight (actor pair + left-to-right ordering), win/loss, runtime targeting authority, the trigger event bus, the component registry, **and the `Timekeeper`'s lifecycle**. The `Run manager` does **not** touch the Timekeeper (the user was explicit) — it hands a fight to the Combat manager and waits for the result.
5. **`StatusManager` = stateless-rules autoload.** Status *instances* live on their **targets** (Actor / Item), not in the manager — purely so the autoload holds no per-fight state. (Statuses themselves are combat-scoped, never run-persistent — **#26**; instances-on-targets is *not* a persistence mechanism.) **Block** = an actor-targeted **absorb-status**; `Actor.take_damage` runs incoming damage through the target's modifier-statuses via the StatusManager (block absorbs before HP; precise amplifier/absorber order is open — StatusManager PRD). Block **persists until consumed** (no decay) and absorbs all damage except `unblockable` payloads — a **per-effect** flag (varies by DoT), not a blanket DoT rule.
6. **Relics & potions = run-level** (player run-state `{ actor, relics, potions, … }`), **not** Actor-owned — keeps the Actor a pure, symmetric combatant (HP + board + statuses).
7. **Symmetric `Actor`; `Enemy` is not a class** — an Actor built from an authored *enemy definition*. Enemy items are a **content category** (per-enemy attack item + small shared utility pool), mechanically just `Item`s.
8. **`Delivery` + `payload`.** What an item fires = a **Delivery** (the in-flight carrier: `payload` + resolved target + travel-Ticker); its content = a **payload** `(kind, value)`. Retired "effect" as the combat-resolution word (overloaded). The item declares a **relative target-shape** (self / opponent-leftmost / all-opponents, + enemy-item shapes — see #14); the **Combat manager resolves shape→target and spawns the Delivery** — so the Item never depends *up* on the Combat manager.
9. **Fixed timestep (the big one).** Combat runs in fixed `STEP`s. The **`Timekeeper` is slimmed to the combat clock**: `sim_time` (stepped, for logic), `render_time()` (continuous, for the smooth VFX wall), the one speed `dial`, and `steps_due()` (real time × dial → whole steps, `MAX_STEPS` cap + backlog-drop) + `advance()`. The **`Combat manager` owns the component registry, advances every component each `sim_step()`, and runs the `_physics_process` loop**. The **dial = how many fixed steps run per real second** (not a per-step delta). This gives determinism + **bit-reproducible autotest** (run K steps); `render_time` keeps motion smooth between steps; Godot's physics loop handles the fixed-`delta` cadence + catch-up cap; **autotest drives `sim_step()` directly** (no real time).
10. **Item types:** every item is **active** (ticks); a "trigger" is an **additional event-push on the same accumulator** (the item still ticks — not a separate type); **no passive item type** (passive/always-on effects are **statuses**).
11. **`Save` = push, not pull.** The `Run manager` hands `Save` a snapshot on encounter entry; on launch the `Game manager` reads it back and the `Run manager` rehydrates — `Save` reads no live state. Auto-save on encounter entry, single run slot, **no migration** (`CLAUDE.md`). Snapshot = run-persistent state only (HP, board+enchants, relics, potions, position, **RNG** so resume is deterministic / not save-scummable); combat state is ephemeral, never saved.
12. **Triggers = accrual-only** (combat_model.md's Bazaar lesson — loop-proof). The **event bus lives in the Combat manager**; a push fires on the *next* step → **one link per step** (no in-step recursion).
13. **Autotest scaffolding.** The AI driver is just **another input-intent source** (combat is auto, so it only makes draft / choice / potion decisions); `--speed` = the Timekeeper dial; headless skips the output layer; determinism = seeded RNG. **The decision AI and the `tune` skill internals are deferred.**
14. **Item-targeting (enemy items) = random by default.** Effects that hit an opponent's *items* (silence, item-debuffs) get two shapes — `opponent-item-random` (one) and `all-opponent-items` (all); single-item selection is **random via the seeded combat RNG** (fights stay bit-reproducible). A deliberate exception to the actor rule ("leftmost, never random," for player predictability) — provisional, may become a rule after testing.
15. **`Run manager` split into `Game manager` + `Run manager`.** The old "Run manager" had grown to own session, run, *and* save concerns. Split by lifetime: **`Game manager`** (autoload `Game`, session-lifetime) owns the **game-state machine** (title → run → death → meta), the **run lifecycle** (create / resume / end the run), and the **save-lifecycle** calls (`read` on launch, `clear` on death/win, meta-save) + global "call-from-anywhere" hooks. **`Run manager`** (instanced per run) owns the **map + encounter sequencing + player run-state + HP-economy**, and **writes** the per-encounter snapshot. Completes the per-lifetime orchestrator pattern — **Game (session) → Run (descent) → Combat (fight)**. *`Game` is an autoload by deliberate exception:* a session-lifetime singleton holding session state matches the autoload lifetime (nothing to keep "fresh"); the guardrail is that **per-run state stays in the instanced `Run manager`** (`Game` holds only a reference, null between runs).
16. **`Encounter` = the per-beat tier; the choice layer's *assembly* is the `Run manager`'s.** An `Encounter` is one resolved beat (fight / event / rest), instanced per beat by the `Run manager`; a fight `Encounter` creates the `Combat manager`. Tier: **Game → Run → Encounter → Combat**. The 2–3 candidate options at a choice point are **drawn by the `Run manager`** (a pool-draw under act constraints + RNG — it owns the map); UI presents; the picked candidate becomes the live `Encounter`. The Encounter is the resolved unit, not the selector; tier-2 within-choices (an event's binary, an elite's engage-by-picking) are the Encounter's own resolution. Rewards: the `Encounter` reports its outcome + reward-kind up; the `Run manager` fulfills it (drives `Draft` / grants the relic).
17. **`Draft` = a stateless reward-draw service.** `Draft` (autoload, like `StatusManager` / `Save`) answers "what candidates to offer" — slot composition (usually item; low chance enchant/potion), **depth-weighting** (rarity odds rise with depth), seeded from the **run RNG** (offer fixed per run-state — no save-scum). The **`Run manager` holds the pending offer and applies the pick** (board / potion / enchant-target / relic); `Draft` writes nothing. **Weighting is depth/rarity only — never the build/archetype** (the design's rejected hidden-weighting). ~~**No skip** (no cap → taking one is always correct; the decision is which).~~ **Reversed by #33 — a draft can now be skipped to bank gold** (the escape hatch from an anti-synergy draft).
18. **The next encounter approaches from depth (created after the draft).** Rather than advance-then-spawn, the `Run manager` **creates the next `Encounter` right after the reward/draft** (spawning its enemy `Actor`s at the vanishing point) and **auto-saves** (encounter entry); the corridor advance then **animates the approach** — the enemies scale up from depth into full view, so the walk *is* the encounter arriving, not dead time. **Resolution begins on arrival** (a fight `Encounter` creates its `Combat manager` then). The approach is presentation (corridor renderer + UI); the logical beat is the resolution.
19. **Content layer (Relic / Enchantment / Consumable) → one combined PRD, prototype-scope.** The three were referenced across the loop but unspecced; they're **thin** (lean on `StatusManager` / `Combat manager` / `Item`), so one `content.md` covers all three rather than three files. A relic = a persistent run-state modifier (combat-start status / triggered Ticker / direct mod); an enchant = a one-per-item modifier hooking the host item's fire/resolve; a consumable = a manually-fired reserve (a Delivery on throw, no Ticker). Split the file later if one grows. All three are **`Draftable`s** alongside `Item` (drafted / inspected / tooltipped); Enchantment differs only in *application* — it attaches to a chosen item, not its own slot.
20. **The `Run manager` owns the run RNG; its full state persists through save/load.** A single seeded PRNG drives all run-level randomness (draft offers, encounter assembly). The snapshot saves the **full RNG state** (not just the seed), so a reloaded save reproduces the **same future outcomes every time** — deterministic resume, no save-scumming a bad draft by quit-reload. Per-fight combat randomness (random item-targeting, #14) draws from a **derived per-fight stream** (run seed + encounter index), so combat doesn't perturb the run stream and a re-entered fight replays identically.
21. **`Draftable` = a composition contract, not a parent class.** What a draft can offer (item / relic / consumable / enchant) shares a **definition-face** (`id / name / icon / rarity / category / tooltip`) by composition; `Draft` + inspection are **category-blind**, and **application dispatches on `category`** (the one switch, in the `Run manager`). The **runtime entities stay distinct types** (they share almost nothing at runtime — a parent class would be a near-empty fat base). Consistent with the Ticker (owned, not subclassed) and Status (data + type key). `category` is **open** — adding a kind is additive.
22. **Entity model is already ally-ready — keep it that way (deferred experiment).** Two families — **`Actor`** (player + enemy, unified by symmetry) and **`Draftable`** (#21) — make "drafting allies" *additive*, not a refactor: an ally = a `Draftable` (`category: ally`) whose application spawns an `Actor` on the player's **side**. The `Combat manager` is already side-relative + list-based (N-vs-M in the abstraction; only 1-vs-M exercised today); the open `category` absorbs the new kind. **Don't build it now** (prototype stays 1-vs-M); **don't over-unify** (no über-`Entity` base over `Actor` + `Draftable` — they share nothing at runtime). The only single-player assumption is run-state's singular `actor` + its snapshot — cheap to change later (no save migration). **Forward-compat rule:** treat each side as a *party* (a roster of 1 today); don't hardwire "exactly one player `Actor`." Same "side = roster" need as the deferred summoning item.

23. **Content definitions are authored in GDScript, not data files.** Item / enemy / status / encounter / relic / enchant / consumable definitions are typed `RefCounted` def objects (`ItemDef`, `EnemyDef`, …) carrying the `Draftable` header by composition, constructed in a **static per-kind catalog keyed by a string id** (amended 2026-06-07 from an int `enum Id` to string ids — `ItemCatalog.WEAPON == 'weapon'` — so content files can be added/removed without editing a central enum). No JSON / `.tres` / inspector — author everything in code (the Slay-the-Spire-2 approach; chosen over last project's JSON, to try). Localization is preserved: source English on the def, displayed via `tr(def.name)`, with the catalog files added to the POT extraction list. Resolves the item / status / enemy / encounter / content data-format opens. *(The `Save` run-snapshot serialization format is separate and still open — it stores ids + runtime values, not defs.)* *(Organization, 2026-06-07: each kind's defs + catalog live in a grouped subdir — `src/content/{items,enemies,relics,consumables,enchants,encounters,statuses,characters}/`.)*
24. **Deterministic component order = a monotonic `seq_id`.** The `Combat manager` stamps each registered component (item Ticker / status / Delivery) an incrementing `seq_id` at registration and advances its registry in ascending `seq_id`. Registration order is itself deterministic (board order at fight start, then the deterministic fire order each step), so the sweep is bit-reproducible. Simplest thing that works — resolves the Combat-manager *within-step component order* open. *(Phase 1 realization, 2026-06-05: the sweep is built as fixed type-ordered passes — item cooldowns → statuses → Delivery travel, each in insertion order — which delivers the same deterministic, bit-reproducible order. A literal `seq_id` counter field is deferred until components of different types must interleave by registration time, which Phase 1 never requires.)*
25. **The scene tree is a logic tree under the `Game` autoload plus a separate presentation tree (the main scene).** Combat logic is plain `RefCounted` (`Actor`, `Item`, `StatusEffect`, `Delivery`, `Timekeeper`, event bus); only the three orchestrators (`Run manager`, `Encounter`, `Combat manager`) are `Node`s, and only the `Combat manager` runs `_physics_process`. The presentation tree reads the logic and emits intents but never mutates it, so a headless autotest simply does not mount it. The framed-versus-full-screen question stays isolated to the one swappable `CombatView` sub-scene. Home: [`architecture.md`](systems/architecture.md#scene-tree--node-model).
26. **Statuses are combat-scoped; run persistence is relics and enchantments (2026-06-05).** Every status is created during a fight, cleared at `CombatManager.teardown()`, and never saved. Statuses are dynamic combat states with no coherent cross-fight meaning: you do not carry a half-consumed shield pool or a ticking poison between fights. Durable state lives one layer up, in a relic (run-level, saved) or an enchantment (permanent item modifier, saved on the board), which re-applies a fresh combat-scoped status each fight where needed. The run snapshot therefore never serializes status instances. Corrects the framing in #5 that item-buff statuses could outlive a fight; that is the enchantment's job. Homes: [`status_manager.md`](systems/status_manager.md) / [`save.md`](systems/save.md).
27. **Item pools are per character, departing from the single shared pool (2026-06-07).** Each character draws from its own pool. A 1-of-3 draft with no hidden weighting cannot be both wide and connective from one pool; per-character pools put focus per run and range per game, so pools can be smaller and deeper. A shared neutral commons layer was considered and rejected. Individual colorless items are not banned, but colorless is the exception that earns its place, never a default tier characters depend on. Only item pools split: enemies and the reward-relic pool stay shared, because per-character everything is the scope trap. Full reasoning, including what to watch in the prototype: [`design/per_character_pools.md`](design/per_character_pools.md).
28. **A shared status baseline is available to every character, starting with Vulnerable and Weak (2026-06-08).** Generic debuffs come from a shared vocabulary so each character's bespoke statuses can stay few and deep. This is not a reopening of #27: #27 rejected a shared *item* layer, and the appliers still live in each character's own pool. Home: [`status_manager.md`](systems/status_manager.md); the Spore Druid's own statuses are in [`design/spore_druid.md`](design/spore_druid.md).
29. **Statuses are polymorphic `StatusEffect` classes, not a central rulebook (2026-06-10).** Replaces one `StatusManager` switching on a status shape with a class per status, each owning its state and its behaviour through overridable hooks that default to no-op. A central switch does not scale to many statuses with wildly different effects, and a class per status lets the engine stop naming statuses by id. `StatusManager` becomes a stateless facade that loops a target's statuses and calls hooks, preserving deterministic order (#24) and amplify-before-absorb (#6). Hooks receive `(target, ctx)` so a status holds no target reference, keeping the no-cycle invariant from #5 and #26. Duration rides the application rather than the status type, and reapplying stacks by default. Supersedes the rulebook framing in #5. Home: [`status_manager.md`](systems/status_manager.md).
30. **Gate freeze, own-side trigger default, and the potion exemption (2026-06-13).** Three combat-semantics calls from the full codebase review. (a) A gated item's cooldown freezes rather than accruing, because a lifting silence used to release the whole backlog at once, which made silence a damage amplifier. (b) A trigger subscription defaults to its own side, so an item reads "when my side does X" unless its definition opts out through `source_filter`. (c) Thrown consumables are exempt from the thrower's combat modifiers: potions are the reserve rather than the engine, so Weak does not scale a potion down and Blind cannot whiff a throw. Homes: [`item.md`](systems/item.md) / [`combat_manager.md`](systems/combat_manager.md) / [`content.md`](systems/content.md).
31. **The combat item tooltip is a cluster driven by a point-poll, with per-keyword information through Godot's built-in custom tooltips (2026-06-19).** Hovering a board item shows a main panel plus an always-shown keyword column beside it, and each keyword chip carries a built-in custom tooltip so the engine owns sub-tooltip positioning rather than us. The cluster is driven by a point-poll off the run screen's existing hover rather than per-cell signals, because the floating cluster needs a per-frame rect check anyway. Displayed values are read-only and must never call `fire()`, which mutates. Keywords are catalog-gated: a missing card is the gate. The copy and colour treatment are the owner's, scaffolded as marked placeholders. Home: [`tooltips.md`](systems/tooltips.md).
32. **The interface reads as roughly 360p on a true high-resolution canvas, and fonts stay smooth (2026-06-22).** The window stays a real 2560x1440 `canvas_items` canvas with no low-resolution framebuffer. The interface is designed to read as chunky pixels but rendered at full resolution so text can be smooth, which is the deliberate opposite of the integer-viewport route that pixelates fonts by design. `UI_SCALE` is a sizing unit, not a transform: chrome is authored at final size, because `Control.scale` fights anchors and `Theme.default_base_scale` is unreliable. There is no pixel-snapping render setting, since it would break the corridor's sub-pixel scroll; the rule is integer at rest, smooth in motion. The corridor half of this decision was replaced by #36. Home: [`ui_theme.md`](systems/ui_theme.md).
33. **A draft can be skipped to bank gold; gold exists as run-state with no sink yet (2026-07-08).** Every item-reward draft offers a skip that banks gold and clears the offer. This reverses #17's no-skip rule: with no cap, taking one is always correct, but that forces an anti-synergy item onto a focused build, and skip is the escape hatch. Skip is an option on every draft rather than a new reward variant, so an elite's relic is still granted. Gold persists in the run snapshot with no migration. There is deliberately no sink until shops exist, so this ships the source and the plumbing, not the economy. The autotest never skips by default, which keeps existing baselines byte-identical. Player-facing copy is placeholder English. Homes: [`draft.md`](systems/draft.md) / [`run_manager.md`](systems/run_manager.md) / [`save.md`](systems/save.md).
34. **Items carry five inert type tags (2026-07-09).** `ItemDef.types` holds any of `weapon`, `armour`, `skill`, `spell`, `trinket`. The axis is the source or vessel of the effect. Nothing keys off them yet and the fire pipeline never consults them; they exist so a future synergy can read tag membership. It is an array rather than a single field so a rare item can carry more than one later. Tags are scoped to items: relics, enchantments and consumables are separate `Draftable` categories (#21) and stay untagged, because those modify an item rather than being one. Genuinely ambiguous items carry an `owner: confirm` comment for the owner to correct. Home: [`item.md`](systems/item.md).
35. **The status fire-hooks carry the firing item, enabling type-scoped synergies (2026-07-09).** `modify_outgoing` and `on_owner_item_fired` both receive the firing `Item`, so a status can tell a weapon attack from a spell or skill. The `item` parameter is optional, so non-item callers and blanket statuses such as Weak are unaffected. `modify_outgoing` must stay pure, because it also runs on the read-only tooltip preview path; anything that spends a charge belongs on `on_owner_item_fired`, which only runs on a real fire. The first consumer is the Smith empower. Bleed used this hook until #38 moved it to `on_holder_attacked`. Homes: [`status_manager.md`](systems/status_manager.md) / [`item.md`](systems/item.md) / [`design/smith.md`](design/smith.md).
36. **The corridor is a real 3D scene; enemies are lit `Sprite3D` nodes in it (2026-09-15).** `Corridor3D` is the only corridor: the two 2D corridors (`CorridorScaled`, `CorridorPerspective`), their `CorridorRenderer` base class, the sharp-bilinear shader and the drop-in `corridor_panel` scene are removed. Each enemy is a `Sprite3D` inside the corridor's 3D scene, lit by the corridor light (so it darkens with distance like the walls), with alpha scissor for transparency (no alpha blending). Only the cut-out painted images remain; the uncut paintings and the pixel sprite are gone as enemy image options. This replaces the corridor part of #32 (the fractional-scale 2D corridor with its filter-while-moving trade); #32's UI and font decisions stand. Home: [`corridor_3d.md`](systems/corridors/corridor_3d.md) · [`run_screen.md`](systems/run_screen.md#enemies-in-the-corridor).
37. **Interface images get their own look; glow is applied to specific elements, not as a look effect (2026-09-16).** Post-processing on the interface runs only on images (icons, portraits, HP bars) through one shared material set in their scenes, never on text or panels, and shares its effect code with the corridor look so settings can be copied between them. Bloom as a look-wide effect was dropped: each node is drawn on its own, so a glow could not spread past it, and the owner prefers glow applied in a steered way when there is a use for it. 2D HDR is on project-wide, and `InterfaceGlow` switches Godot's screen glow on only while something glows, because the glow pass darkens the whole screen slightly. Home: [`interface_look.md`](systems/interface_look.md) · [`interface_glow.md`](systems/interface_glow.md).
38. **Mechanics: a small, fixed set of combat rules modelled on grail (2026-09-17).** Attack, shield, heal, poison, burn, bleed, regen and crit become mechanics: one class per mechanic holding its name, description, icon, colour and what happens when it lands, so items, relics and enchantments can refer to them by name. Block is renamed shield. Attack is the mechanic for a direct hit; damage means health or shield lost from any source. Statuses outside the set, and summon and item creation, are unchanged for now. Home: [`mechanics.md`](systems/mechanics.md); the original specification is [`plans/mechanics.md`](plans/mechanics.md).
39. **The prototype content is deleted; the roster is the Fleshmancer and the Spore Druid (2026-09-18).** The Wanderer and Duelist placeholder characters, four placeholder items and the shared `DraftPool` are gone, because they were seed data standing in for real characters and two authored characters can now carry a run. `CharacterCatalog.DEFAULT` is the Fleshmancer, the deeper pool. Venom Fang, Spite Ward, Hex Bolt and Sunder stay in the catalog but in no pool, the authored-but-not-drafted state from #27. Tests draw on generic fixtures rather than authored cards, so tuning or renaming content cannot break a combat, interface or event test. Two consequences are content work for the owner: no character has a starting relic, potion or enchant, so those paths are unreachable in a played run; and the default descent's outcome changed with the character. Homes: [`design/authoring.md`](design/authoring.md) / [`content.md`](systems/content.md).

40. **The theme drops the UI pack art; hover, selection and press are drawn by one shared system (2026-09-19).** Every Button state now draws the same flat, palette-following fill, and the pack's button, tooltip and checkbox images are no longer referenced, because the button art was pure black and could not be tinted, which left the text colour as the only hover feedback. What a control does under the pointer is drawn instead by the control highlight: a rough printed border while hovered or selected, a light wash that lifts a plain button's body, a press that completes the hover rather than reversing it, and one ink pulse on release. It is drawn by the panel wear shader into panel wear's own canvas item, so it sits behind the control's text and knows the panel's rectangle; a separate canvas item drew over the text. Border-only is the treatment for anything whose body is a picture, so item cells and character cards read the same way as buttons. Home: [`control_feedback.md`](systems/control_feedback.md) · [`ui_theme.md`](systems/ui_theme.md).

41. **Targeting is pool, then filter, then pick; an item's mechanics are authored (2026-09-20).** An effect's target shape still decides which pool to draw from and how many to take, and an optional **target filter** sits between the two, narrowing the pool by item type tag and by mechanic. This is what lets an item target "all your weapons" or "a random enemy bleed item" without the shape enum growing a value per combination. A filter is a flat list of conditions with one match mode, all or any, so "weapon and poison" and "weapon or spell" are both authorable; nesting is not, and if a card ever needs it the answer is two effects. Filters narrow **item** pools only — actor targeting keeps the leftmost rule for predictability, and a filter on an actor shape warns once and is ignored. The filter matches against `ItemDef.mechanics`, a list **authored** per item rather than derived from its effects, because the hard cases are judgment calls: an item that charges when poison is applied is a poison item, while an item that creates a bleeding dagger is not, and no single rule yields both. One floor is checked in the tests — every mechanic an effect deals or applies must be listed — and everything above it is the author's. Homes: [`item.md`](systems/item.md) / [`combat_manager.md`](systems/combat_manager.md) / [`tooltips.md`](systems/tooltips.md).

42. **The Smith is the default character, enemy health is on the points curve, and whole-run tests use a fixture (2026-09-21).** `CharacterCatalog.DEFAULT` is the Smith, because it is the character being balanced first; it stays out of the character-select roster until the owner adds it. `Balance.ENEMY_*_HP` is raised to the curve's beat 0 target, and the enemy Claw is resized so an early regular fight costs a player with no armour up to 10% of starting health (owner, 2026-09-22); all three characters clear the run with that pair. Tests that play a run, an encounter or an autotest now use a fixture character and fixture enemies installed into the catalogs by `FixtureContent`, extending the item fixtures from #39, so a balance or roster change cannot break them. Homes: [`testing.md`](systems/testing.md) / [`design/smith.md`](design/smith.md).

43. **Enemy health and damage both grow through the run, and enemy items are ordinary items (2026-09-22).** Player damage, healing and shields rise as the board grows, so enemy health and enemy damage rise with them, roughly in step (owner); the per-act points ranges in [`plans/encounter_points_budget.md`](plans/encounter_points_budget.md) set the size. An enemy may carry any item, including one from a player pool, and its items work exactly like the player's. This reverses the earlier guideline that enemy items must not be mechanically identical to player items. Characters and enemies (which include allies and summons) share one definition base, `ActorDef`, so a field such as the corridor image is added once (owner). Which enemies each act meets, and each act's boss, are lists in `EnemyPools`. Home: [`enemy.md`](systems/enemy.md).
